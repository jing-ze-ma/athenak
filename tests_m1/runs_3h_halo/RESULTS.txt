The two halo functions were 12.1 % of the run.  The boundary machinery they
call -- InitRecv, PackAndSendCC, RecvAndUnpackCC, ClearSend, ClearRecv, i.e.
the buffer pack/unpack and the MPI-less copies -- was 0.4 % of the run TOGETHER.
So essentially NONE of the 12.1 % was the exchange: it was the two par_for
copies each function ran between iw and its scratch array, INLINED into the
function (Kokkos::Serial), which is why they showed up as the functions
themselves.  perf annotate confirms it: the hot instructions are `idivl` plus
the index multiply-adds of the flattened RangePolicy (par_for unflattens the 1-D
index with an integer division per index PER CELL), and a single `movsd` pair.

Two wastes, both structural:
  (a) both copies ran over the WHOLE MeshBlock, 88 x 36 = 3168 cells per
      component, although a same-level exchange only ever READS the outermost
      ng active cells and only ever WRITES the ghost zones -- 480 cells.
      6.6x too much work here, and it is a surface/volume ratio, see sect. 4.
  (b) ImplicitTransverseHalo always carried all M1_NHALO_T = 14 components,
      three times per Picard pass, although at two of the three call sites only
      ONE component had moved since the previous exchange.

2.  WHAT CHANGED  (no new user parameter; the default path itself gets faster)
--------------------------------------------------------------------------------
src/rad_m1/rad_m1_implicit.hpp
  * M1HaloCompT reordered so that a PREFIX of the list is a legal exchange:
      0..3  EP, G0, F1, KT        = M1_NHALO_Q, what a pass can still move when
                                    the closure is frozen
      4..10 WCHI, N1..N3, ADV, A2, A3
      11..13 V1, V2, V3           (never move inside a step at all)
    Reordering changes which SLOT of the scratch array holds what; the values
    exchanged per component are untouched.

src/rad_m1/rad_m1_implicit.cpp
  * ImplicitHaloCopy(sc, nq, c0, topack): the single copy routine.
    - SHELL ONLY.  The box [is+ng,ie-ng] x [js+ng,je-ng] x [ks+ng,ke-ng] is
      neither read by a send nor written by a receive (buffs_cc.cpp, isame:
      a same-level buffer reaches ng cells in from the active boundary), so it
      is skipped in both directions: on the way in nothing reads it, on the way
      back it would be a copy of what the pack just put there.  A degenerate
      direction counts as interior everywhere; a direction with nx <= 2 ng
      makes the interior box empty and the copy full.
      Guarded by the new member `halo_shell`, false under SMR/AMR (already a
      fatal for implicit transport), the cubed sphere and the polar boundary,
      whose exchanges read deeper -- those fall back to the full copy.
    - The loop carries (m,n,k,j) and runs the contiguous i direction INSIDE, so
      the flattened-index integer divisions are paid once per ROW, not per cell.
  * ImplicitHaloExchange(nq, c0): pack / InitRecv / PackAndSend / RecvAndUnpack /
    ClearSend / ClearRecv / unpack, on the PERSISTENT array whose width matches
    nq.  Three widths, one array and one MeshBoundaryValuesCC each (thw 14,
    the new thq 4, krw 1).  A prefix subview of a LayoutRight array is not a
    LayoutRight array, and the exchange takes its variable count from the
    array's second extent, hence three arrays rather than one.  They are used
    strictly sequentially, as thw and krw already were, so sharing the MPI tag
    space is unchanged.  krw/pbval_kr are now allocated under every solver (they
    were bicgstab-only), because the E-only exchange uses them.
  * ImplicitTransverseHalo(nq) and ImplicitKrylovHalo(comp) are now thin
    wrappers.  Call sites, per Picard pass:
      pre-loop                          14  (unchanged)
      after the lagged-closure kernel   14, or 4 when the closure is frozen
                                            for the step (implicit_closure_lag
                                            = step, pass > 0)
      after the accept kernel            1  (E alone: the ONLY halo quantity the
                                            pass changed since the exchange
                                            above -- F1 is rebuilt AFTER it)
      after ImplicitAccelApply          14  (it rewrites F1 as well as E;
                                            implicit_accel = none by default)
    Why 4 is enough with closure_lag = step: the pass re-derives ADV/A2/A3 from
    a FROZEN chi, n and v with the same expressions, so they come out
    bit-identical and their ghost layer is still the one the previous exchange
    left; V1..V3 do not move inside a step; EP, G0, F1 always move and KT moves
    under implicit_opac_update.  With closure_lag = pass the closure set still
    goes every pass (the 14-wide exchange), and only the E-only saving applies.
    No kernel writes iw in the ghost zones, so a ghost value stays valid until
    the next exchange of that component.

src/rad_m1/rad_m1.hpp, rad_m1.cpp: thq / thq_c / pbval_tq / halo_shell members,
    the new declarations, the destructor.

--------------------------------------------------------------------------------
4.  HOW THIS SCALES
--------------------------------------------------------------------------------
The part that was removed is a VOLUME cost (copy the whole block) replaced by a
SURFACE one, so the win grows with block size, while what is left (the buffer
pack/unpack) was already a surface cost.  Per component and MeshBlock, cells
copied before / after:

    block (2-D, ng=2)      full      shell     ratio
    84 x 32 (this test)    3168       480       6.6
    64 x 64                4624       544       8.5
    128 x 128             17424      1056      16.5
    3-D 64^3             314432     51200       6.1
    3-D 128^3           2097152    204800      10.2

On top of that the component count of the transverse exchange per Picard pass
went 14 + 14 (+14 under accel) -> 14-or-4 + 1, i.e. 28 -> 5 component-exchanges
per pass in the default (closure_lag = step) configuration, which is a saving in
the buffer traffic and the MPI message size too, not only in the copies.  On a
production-size block the halo share of the implicit solve should therefore fall
further than the 20x measured here, not less.
