CHOICE: exact banded sweep (neither pure A nor KBA B)
--------------------------------------------------------------------------------
The sweep already runs layer by layer in x1 with one launch per layer over the whole
(k,j) plane.  A split in x2/x3 (the production decomposition, 84 x 52 x 52 blocks) does
NOT serialise anything: every block holds the same x1 layer, so all blocks of a layer
run in the same launch; the only extra is a halo exchange of the new intensity plane
after each launch.  So the exact answer costs one band exchange per layer, not a
pipeline.  Only a split in x1 serialises (the stack is swept block after block, with
the upwind plane handed across the face) -- and the x1 line solve already needs
implicit_partition = gather for that, and production has one block along x1.
Hence: EXACT sweep for every decomposition.  Option A was implemented as a DIAGNOSTIC
(<rad_m1>/vet_mb_lag = K) and measured below: it is not good enough.

Implementation (VetSweepMB):
 * banded planes: width w = floor(max_r dx1 |mu_perp/mu_1| / dx_perp) + 1 per side,
   = 4 cells here (reach 3.6 dx2); fatal if a block is narrower than w.
 * launch L = global layer L (up rays) and nx1g-1-L (down rays); blocks that hold
   neither return at once.  Arithmetic identical to the single-block kernel.
 * after each launch: band exchange of the new plane with 2 (2-D) or 8 (3-D, incl.
   corners) horizontal neighbours: device copy on a rank, MPI with device buffers
   (as the boundary machinery does, private dup'd communicator) between ranks.
 * extinction and source: banded copy + x1-face layers exchanged once per call.
 * at L = q nx1: the upwind plane (up rays from below, down rays from above) is moved
   across the x1 face (device copy or MPI in place, planes are contiguous).
 * vet_tensor = full: the six D_ab ghosts go through a MeshBoundaryValuesCC (6 vars);
   edge copy only at a physical x1 face.  Uniaxial (chi,n) needs nothing: the solve
   copies them into iw, whose halo the solver already exchanges.
 * one MeshBlock on one rank: the old single-block code runs unchanged.
   vet_mb_force = true (diagnostic) runs the banded path on one block.
 * vet_dump on several blocks writes one .plane.g<gid> file per block, global (i,j).

Memory added at production size (84 x 52 x 52 block, 64 rays, w = 4, ng = 3), per
MeshBlock (the old path held vet_ipl 2 x 64 x 58 x 58 = 3.4 MB):
   intensity planes 2 x 64 x 60 x 60              3.7 MB   (replaces vet_ipl)
   banded chi,S     86 x 2 x 60 x 60              5.0 MB
   message buffers  2 x 8 slots x 64 x 4 x 52     4.6 MB
     (sized for the largest message, max(nray, 2(nx1+2)) x 208 cells)
   D ghost scratch  6 x 58 x 58 x 90 (full only) 14.5 MB   (+ bvals buffers)
   => ~28 MB per block (full), ~13 MB (uniaxial) by this count (computed, not
   measured).  The start-up line of GPU run S1 (4 blocks, full) prints 111.0 MB of
   sweep buffers on the rank (planes + chi,S + message buffers + D scratch) = 27.8 MB
   per block, as counted.  The lag diagnostic adds nx1g x 64 x 60 x 60 per block
   (155 MB) and is for CPU tests only.
Per x1 face the x1 handoff moves nray/2 x 60 x 60 = 0.9 MB per crossing.
