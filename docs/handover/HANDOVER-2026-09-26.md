## 2. Porting to a new cluster (GPUs, scheduler)

**Build.** There is no globbing: new sources go into `src/CMakeLists.txt`. Always build in a separate
directory, and build the problem generator you need:

```bash
git submodule update --init --recursive           # kokkos
# NVIDIA (pick the arch of the Caltech GPUs: AMPERE80 = A100, HOPPER90 = H100/H200, ADA89 = L40S)
cmake -B build_dhj -D Kokkos_ENABLE_CUDA=On -D Kokkos_ARCH_HOPPER90=On \
  -D CMAKE_CXX_COMPILER=$PWD/kokkos/bin/nvcc_wrapper \
  -D Athena_ENABLE_MPI=ON -D CMAKE_BUILD_TYPE=Release -D PROBLEM=deep_hot_jupiter_rt
# AMD (viper was MI300A: -D Kokkos_ENABLE_HIP=On -D Kokkos_ARCH_AMD_GFX942_APU=On -D CMAKE_CXX_COMPILER=hipcc)
make -C build_dhj -j 16                            # -> build_dhj/src/athena
```

- Problem generators in use:
  - `deep_hot_jupiter_rt`: the hot-Jupiter runs, cubed sphere + correlated-k RT;
  - `box_convection`: the He / massive-star M1 box;
  - none, i.e. built-in pgens, for the tests.
- `docs/handover/caltech-2026-09-26/scripts/build_viper_reference.sh` is the exact viper recipe. It builds
  from a `git archive` snapshot so that a dirty tree never leaks into a binary; keep that habit.
- Check the build with `./build_dhj/src/athena -c`.
- CPU builds are used only for correctness gates, e.g. bitwise comparisons. **All timing and cost
  comparisons must be made on the GPU, same binary, arms interleaved** (user rule).

**Viper-only facts. Do NOT carry them over; re-establish them on Caltech:**
- **GPUs per node.** Viper: 2 MI300A per node. The apudev partition allowed 1 node and 15 minutes; apu
  allowed longer jobs. Find Caltech's GPUs per node, partitions and limits first (`sinfo`, site docs), and
  record them in memory as a Caltech fact.
- **AMD env vars.** Every viper GPU job exported `HSA_XNACK=1` and `HSA_NO_SCRATCH_RECLAIM=1`. These are
  AMD/ROCm (MI300A APU) settings and are irrelevant on NVIDIA. On NVIDIA, check GPU binding instead:
  one MPI rank per GPU, `CUDA_VISIBLE_DEVICES` per rank or `srun --gpus-per-task=1`.
- **Timings.** All ms/cycle numbers in the notes are MI300A numbers. Re-measure before comparing.
- **viper-specific machinery.** Login-node memory caps, the inode quota and the `claude-work.slice` memory
  hook are all viper-only.

**Job scripts.** `scripts/run_viper_reference.sub` is the viper Slurm driver for the WASP-121b runs. Its
logic is portable:
- planet selection;
- the key groups T4 / C2 / E4;
- sponge arms;
- restart from the newest rst;
- `-t` wall-clock stop, with a STOP file so chained links skip finished arms.

Rewrite only the `#SBATCH` header, `module load` and the `srun` line for the Caltech scheduler. If Caltech
is not Slurm (e.g. PBS), keep the body, translate the header, and replace `--dependency=afterany:` chaining
with the site's equivalent. Note that Slurm snapshots the script at `sbatch` time: after editing a submit
script, cancel and resubmit.

## 7. Working rules from the user (portable)

- **No accuracy sacrifice for speed.** Speed-ups must be accuracy-neutral in the region that counts: the
  deviation from the reference must be no larger than the reference's own ROUND-OFF spread (1 vs 2 GPUs, or a
  1e-14 kick). The time-discretization error is not the bar (user 09-26).
- **Two phases (user 09-26): cheap schemes are allowed during relaxation, accurate schemes at the steady
  state.**
  - Relaxation / spin-up may use multi-rate, the ck cadence e8 + x16, `vet_col_every`, a looser Picard tol,
    or a cruder top treatment, if the run is stable.
  - Then switch to accurate settings and check that the deep T and flux do not drift afterwards.
  - The measured steady state uses only round-off-neutral speed-ups, except the step size: hesdirk2 at cfl
    0.9 is kept in both phases.
  - Memory `two-phase-relax-then-accurate`.
  Multi-rate and similar levers are opt-in, never recommended as defaults.
- **Measure cost on the GPU**, same binary, interleaved arms, repeats. CPU runs are for correctness gates.
- **Merge finished, gated branches into `rt-integration` promptly and push to the fork.** Gates:
  - new keys default off and bitwise with the keys off;
  - restart bitwise;
  - the relevant test suite and style checks (`cd tst && python run_test_suite.py --style`).
- **Jobs:**
  - no blocking sleep/until loops in the foreground;
  - submit, check once, return control;
  - a background poll every 10 min is fine;
  - no heavy or rolling monitoring.
- **Agents:** one deliverable each, narrow prompts. Report only results, decisions and failures, not
  "still waiting" acknowledgements. No new side threads without asking the user.
- **Never write into `run/`**: old output, gitignored.
- **Keep login-node analysis memory modest:** at most 40 GB, one dump at a time.
- **Housekeeping at minimal token cost.**
- **Before claiming a machine fact** (GPUs per node, partition limits), check it with the scheduler.
  Mistaking this was a recurring error on viper.
